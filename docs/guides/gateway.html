Phone tool gateway: one small, stable tool surface for a local model

The code is in gateway/. It runs on the PC behind mcpo, and Open WebUI on the phone talks to it as a single tool server. The measurements below come from one Intel Arc Pro B60 running Qwen3.8-27B, llama.cpp b11524 on Vulkan, on 2026-10-11.

What problem it solves

Qwen's chat template writes every tool schema at the start of the prompt (TOOL-CALLING.md). That has three consequences:

  • Every loaded tool costs prompt tokens on every request.
  • Changing the tool set throws away the prompt cache.
  • Loading the whole PC agent, browser and desktop tools came to 18K tokens, and the first message took 39 s.

The gateway shows the model a fixed set of tools:

  • seven pinned basics: pc_Read, pc_Grep, pc_Glob, fetch_fetch, time_get_current_time, skills and share_file;
  • search_tools(query) and call_tool(name, arguments), which reach everything else.

Behind those, nine MCP servers serve about 100 tools: Claude Code's tools, the filesystem, fetch, time, library docs, a headless browser, the user's own Chrome, the Windows desktop and MarkItDown. A tool's schema costs nothing until a search returns it. The search result lands at the end of the conversation, so the cached prefix survives.

Phone eval (10 prompts, 2026-10-11)

gateway/tests/phone_eval.py gives Qwen the phone system prompt and the gateway's tools through mcpo. It has eight read tasks and two safety checks. Each case allows at most 8 model turns.

10/10 passed. Median 10.3 s per task, 149 s for all ten. 64,108 of 71,554 prompt tokens (90%) came from the cache. The first case includes a cold prefill of the tool set and system prompt (2,823 tokens). The model answered 8 of 10 cases with pinned tools alone, no search needed. It found the converter through search_tools on its first try. It stopped at the approval for the delete, and it reported the policy block on the gateway's config instead of working around it. How it works

PartFileWhat it does
Proxygateway.pyOne kept-alive stdio client per server, mounted as <server>_<tool> (FastMCP 3.4.8; 4.x rejected older servers). Optional servers are probed in a thread with a timeout, so a Chrome extension that is not connected cannot hang startup.
Searchgateway.pyBM25 over names and descriptions, with aliases and light stemming. Hidden tools never show in results. An unknown tool name returns the closest matches instead of a stack trace.
Harness textprompts/phone-system.md, descriptions in the configRules the model was missing: search before saying "I can't", use exact names, keep output small, the approval flow, and VERIFIED/INFERRED labels.
Guardgateway.pyKill switch file, deny rules for tools and arguments, read/write/destructive intents, rate and loop limits, results trimmed to 12,000 characters, and a hash-chained audit log.
Approvalsapprovals.pyWrites and deletes wait for the owner. The owner approves on a PIN-protected page (PBKDF2 hash, HttpOnly cookie), and the model then repeats the identical call. The model never sees the PIN.
Skillsskills.pyskills(action="search"|"load") over local SKILL.md folders (154 on the test PC) for about 120 prefix tokens, instead of every skill in the prompt.
Shareoutbox.pyshare_file(path) copies a file or folder from an allowed root into an outbox and returns a token link (128-bit token, expires after 24 h). Links are served behind Content-Security-Policy: sandbox, so model-written HTML cannot use the approvals page's cookie.
Live statsopenwebui/live_stats_filter.py, voice/tts_server.py /statsTokens per second, context use, cache hits and the governor profile. Profile buttons switch MAX/BALANCED/LEAN and need the PIN session.

Startup

The old setup started eight stdio servers twice, once in mcpo and once inside the gateway. It also resolved npx and uvx packages on every start.

The new setup runs a single gateway behind mcpo, with the servers installed as executables. On the test PC:

  • the gateway is ready in 18.6 s, down from about 100 s for the whole tool hub;
  • mcpo answers in about 25 s.

BALANCED's idle model unload moved from 30 to 120 minutes, so the first message after a break is less likely to pay a 17 GB model load.

Install (Windows)

  1. Create a venv in C:\AI\gateway and install the gateway: python -m venv .venv then .venv\Scripts\pip install fastmcp==3.4.8.
  2. Copy gateway.example.json to gateway.json. Fix the paths, and put tokens such as PLAYWRIGHT_MCP_EXTENSION_TOKEN in the copy only, never in git.
  3. Point mcpo at the gateway alone; see mcpo.config.json and start-mcpo.ps1.
  4. Run set-approval-pin.ps1 on the PC to set the approval PIN. With no PIN set, nothing can be approved.
  5. In Open WebUI, add the tool server and use Native function calling. connect_gw_openwebui.py does this from the command line.
  6. Run the tests from gateway/: python tests/test_gateway.py (11 checks) and python -m unittest tests/test_outbox.py (27 tests).

Limits and next steps

  • The eval cases are single-step jobs. Multi-step builds ("make me a website") still depend on the model working through a long loop in Open WebUI. The next step is a server-side agent tool, a plan-act-verify loop inside the gateway with its own todo list and the same guard; see the harness plan.
  • Each search-then-call costs one more model turn. Pinning the most-used tools avoids that for reads.
  • Anyone on the tailnet who holds a share link can fetch that file until it expires.
